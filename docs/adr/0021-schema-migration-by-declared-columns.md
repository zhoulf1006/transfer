# ADR-0021: 表结构迁移用「列声明单一事实源 + 按需补列」,不引版本号

状态:已采纳(2026-08-22)

## 背景与问题

给消息表加第一个新列(传输耗时)时才发现:**这个项目从来没有迁移机制**。`migrate()` 里只有一句 `CREATE TABLE IF NOT EXISTS`,而全历史从未出现过 `ALTER TABLE`(`git log -S` 零命中)。

按最自然的写法——把新列加进建表语句——会出事,而且出得很隐蔽:

- **新装用户**:表是新建的,一切正常;
- **老用户**:`CREATE TABLE IF NOT EXISTS` 对已存在的表是 **no-op**,新列根本不会被加上,第一次写就 `table messages has no column named ...` 抛异常 —— 表现是**升级后一发文件就失败**,不是"少个功能"。

要命的是这条路径**只在"老库 + 新代码"这个组合下才走**。日常开发时库都是新建的,永远碰不到;测试如果也用新建库,同样碰不到。

## 备选项

1. **版本号 + 迁移脚本列表**(经典做法):库里存一个 `user_version`,按版本逐步执行迁移脚本。表达力最强,能处理改类型、拆表这类复杂变更。代价:同一件事记两笔账 —— 列是否存在本身就是可查的事实,再维护一个版本号意味着两者可能不一致(手改过库、迁移半途失败),而不一致时以谁为准没有答案。
2. **每次启动全量比对并补齐**:查 `pragma_table_info`,声明里有而库里没有的就 `ALTER TABLE ADD COLUMN`。
3. **建表语句里加列,老库不管**:即上面那个会出事的写法。

## 决策

取备选 2,并把**列声明提成单一事实源**:建表语句与补列逻辑都从 `MESSAGE_COLUMNS` 派生。

- 加列时只改那一处,**"加了列却忘了写 ALTER"在结构上就不可能发生**;
- 不引版本号:列是否存在可以直接查,状态即事实,不需要第二本账;
- 每次启动跑一遍,**幂等**(已有的列跳过)。

配套两条硬约束:

- **新增列必须可空**(不写 NOT NULL、也不给默认值)。两个理由:①有数据的老库补列时 SQLite 会拒绝"NOT NULL 且无默认值";②用户装了新版写了库、再降级回旧版时,旧版的 INSERT 不带新列 —— 列不可空就写不进去。
- **改表结构时,把改动前的建表语句作为快照追加进迁移测试**,测试遍历"从每个历史版本升上来"。

## 后果

**得到**:升级对用户完全无感,不需要任何操作;"忘了补列"这类错误从"靠人记得"变成"结构上不可能";迁移路径有了自动化门禁,而在此之前它连一次都没被执行过。

**失去 / 已知代价**:

- 只能表达**加列**。改类型、改约束、删列、拆表都不在这套机制内 —— 真要做时得另立方案(那时也该重新审视要不要引版本号)。
- **"新增列必须可空"这道约束不能靠 SQLite 替你把关**:实测它**只在有数据的表上才拒绝**,空表照样能加。也就是说开发时(新建库)发现不了,只有老用户升级才炸。约束靠人守 + 靠迁移测试的降级用例守。
- **历史快照要人记得追加**。漏了不会有任何东西报错,只是从那个版本升级的路径失去覆盖。提示写在测试文件头,但那仍是"靠人读到"。
