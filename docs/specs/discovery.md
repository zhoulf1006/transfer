## Problem

两台机器要互传,先得找到彼此。手动输 IP 的门槛太高,而且 IP 会变(DHCP 续租、换网、睡眠唤醒)。用户要的是打开 app 就看到对方,不做任何配置。

难点不在"怎么广播",而在**网络环境不受控**:机器上可能装着代理软件(隧道网卡会抢走多播)、可能有多块真实网卡(VM、WSL、有线+无线同时在)、路由器可能屏蔽多播、企业网可能抑制广播。这些都不能靠"再加一条通道"解决,只能各自识别并如实告诉用户。

另一个约束来自**安全立场**:不扫网段。扫描像横向渗透,会触发企业 EDR,代价远大于收益(ADR-0005)。

## Solution

**主动宣告 + 定向回应**两段式:

- **announce**:UDP 主动宣告自己存在,**同时走多播与子网定向广播两条通道**(ADR-0006)。两条都发是因为它们的失败原因不同——多播可能被路由器屏蔽或被隧道网卡抢走,广播可能被企业网抑制;同时发提高常见家用/办公场景的成功率。
- **register**:收到别人的 announce 后,**走 HTTP 定向回应**对方(ADR-0005),而不是回一个 UDP 包。定向回应天然只联系"确实存在的那台",不产生扫描行为。

设备身份用**自签名证书的 SHA-256 指纹**(ADR-0002):它跨重启不变,与 IP、名字都无关,所以对方改名换 IP 后仍是同一台设备,备注与聊天记录不丢。

## User stories

- 作为用户,我打开 app,同网的其他 Transfer 数秒内出现在列表里,我什么都不用配。
- 作为用户,对方关掉 app 后,我看到它变灰置底而不是立刻消失——万一只是暂时退出,我不想丢掉这条会话。
- 作为用户,对方换了 Wi-Fi 或改了名字,我看到的还是同一台设备,备注和聊天记录都在。
- 作为用户,如果因为网络环境根本发现不了,我希望 app 别假装在找,而是让我知道这类网络就是不行。

## 失败模式与边界穷举

标注:**〔测〕**=有自动化用例驱动;**〔实〕**=靠实测/抓包坐实(非自动化);**〔缺〕**=已知未覆盖。

### A. 报文与自我过滤

| 边界 | 期望行为 | 覆盖 |
|---|---|---|
| 收到**自己**的 announce(多播天然会回环) | 按指纹比对丢弃。**多播与 HTTP 回应两个入口都要做**——只做一边会从另一边把自己加进列表 | 〔测〕 |
| 收到 `announce=true` | 触发定向回应 | 〔测〕 |
| 收到 `announce=false` | **不回应**。回了会两端无限对回 | 〔测〕 |
| 非法报文(字段缺失、类型不对、JSON 坏掉) | 静默忽略,不触发上报、不崩溃 | 〔测〕 |
| 回应报文里省略了端口 | **不能拿它刷新登记**——会用默认端口覆盖掉对方的真实端口,之后连错端口 | 〔缺〕 |

### B. 网络接口选择(踩过真实 bug 的地方)

| 边界 | 期望行为 | 覆盖 |
|---|---|---|
| 机器上有代理隧道网卡(Clash/Surge 的 utun,`198.18/15`) | **必须排除**。不指定接口时操作系统可能把多播加到隧道上,导致同网设备互相发现不了——这是实测过的真实 bug | 〔测〕 |
| Tailscale 的 CGNAT 段(`100.64/10`) | 同上排除 | 〔测〕 |
| 回环接口 | 排除 | 〔测〕 |
| **多块**真实局域网网卡(VM/WSL 网卡与真实 Wi-Fi 撞私有段) | **每块都要加入多播组、每块都要发 announce**,不赌单一接口 | 〔测〕 |
| 一块真实网卡都没有(全是隧道) | 退回让操作系统决定,不硬选一个错的 | 〔测〕 |
| 网卡的掩码非法或地址异常 | 跳过该网卡,不让一块坏网卡拖垮整轮 | 〔测〕 |
| 子网广播地址的计算 | 按掩码算,**非整字节掩码也要对**(/25 之类) | 〔测〕 |
| 广播是否需要显式设出接口 | **不需要**——广播按目标地址路由。原实现里那段是冗余,已去掉 | 〔实〕 |
| 广播是否要另开 socket | **不要**——复用多播 socket 零冲突 | 〔实〕 |

### C. 端口

| 边界 | 期望行为 | 覆盖 |
|---|---|---|
| 约定端口被占(本机已有官方 LocalSend,或残留实例) | **HTTP 端口向上回退**;**UDP 多播端口固定不动**——变了就收不到别人的广播 | 〔测〕 |
| 回退之后 | 宣告里带的必须是**实际**的 HTTP 端口,两者可以不同 | 〔测〕 |
| 同一台机器上跑两个实例 | 接收 socket 必须允许地址复用,否则第二个实例起不来;两个都收得到,再各自按指纹过滤自己 | 〔测〕 |

### D. 设备状态与生命周期

| 边界 | 期望行为 | 覆盖 |
|---|---|---|
| 新设备出现 | 默认在线,列表可见 | 〔测〕 |
| 同一设备重复宣告、信息没变 | 只刷新最后可见时间,**不报告变化**——否则界面每几秒重绘一次 | 〔测〕 |
| 地址或名字变了 | 报告变化,界面刷新 | 〔测〕 |
| 离线设备重新上线 | 转回在线并报告变化 | 〔测〕 |
| 超过在线判定时限 | 转离线(灰显置底),**不立刻删除** | 〔测〕 |
| 离线后超过保留时长 | 才真正删除。**两段式**,不是一步到位 | 〔测〕 |
| 用户把保留时长**改长** | 本来要删的设备被留住 | 〔测〕 |
| 用户把保留时长**改短** | 已超新阈值的下次清理即删 | 〔测〕 |
| 用户设成"永不移除" | 离线设备永远留着,时钟推进再久也不删 | 〔测〕 |
| 从"永不移除"改回有限值 | 积压的超期设备下次清理批量删掉 | 〔测〕 |
| 设置里写进了非法值(NaN/undefined) | 忽略并保留原阈值,**不得静默变成永久** | 〔测〕 |
| "永不移除"的内部表示 | 运行时用无穷大,但**绝不能写进配置文件**——序列化后会变成 `null` 把配置写坏 | 〔测〕 |
| 一轮清理没有任何变化 | 不触发界面刷新 | 〔测〕 |

### E. 信任与回应

| 边界 | 期望行为 | 覆盖 |
|---|---|---|
| 回应对方的宣告时,本机还没有对方的指纹 | **这是指纹校验的唯一例外**:回应走不校验的通道。强行校验会 fail-closed,导致对方永远发现不了我方,双向发现塌一半 | 〔测〕 |
| 传输相关的请求(协商/传输/取消) | 一律走校验指纹的通道 | 〔测〕 |
| 对端证书指纹与登记的不符 | 传输失败,不静默放行 | 〔测〕 |
| 本机压根没有对端指纹 | fail-closed,响亮失败 | 〔测〕 |

### F. 网络环境的能力限度(不是 bug,是边界)

这些场景**无法在应用层解决**,写在这里是为了下次收到"发现不了"的反馈时不再重走死路:

| 场景 | 现象与结论 | 覆盖 |
|---|---|---|
| AP 客户端隔离 | 多播与广播**同时**被切断,两条通道一起失效 | 〔实〕 |
| 企业网广播抑制 | 广播兜底失效 | 〔实〕 |
| 跨网段 / VLAN | 广播出不去 | 〔实〕 |
| 对方开 VPN 全隧道 | **能发现但发不过去**——发现走 UDP 没被劫持,而到局域网 IP 的 TCP 被灌进隧道黑洞。表现是列表里有它、一发就连接超时 | 〔实〕 |
| macOS 首次多播 | 可能触发本地网络权限询问 | 〔实〕 |

**推论(最重要的一条)**:落在上面前三种场景时,**再加一条发现通道不会有任何帮助**。要解决只剩扫网段(已因安全立场排除)或中心服务器(与无服务器架构冲突)。收到这类反馈先判断是不是这三种场景,别重复走这条死路。

## 测试决策

- **接口选择、广播地址计算、设备生命周期这三块用纯函数 + 单测**:它们的输入(网卡列表、掩码、时钟)都能构造,而真实网络环境无法在 CI 里复现。这是**有意把可测的部分从不可测的部分里剥出来**。
- **时钟注入**:生命周期的两段式(转离线 → 真删)靠注入时钟推进,不靠 sleep。
- **真实报文收发有一条端到端用例**(两个实例互相发现且不发现自己),其余靠单测。
- **网络环境类的边界一律不写自动化用例**,靠实测记录在复盘里。理由:它们需要特定的路由器/AP 配置,CI 里造不出来,硬写只会得到一条永远跳过或永远绿的用例。
- **诊断手法本身也是产物**:发现类问题靠抓包定位,不靠读代码推理——手法记在复盘里,下次直接照做。

## 明确不做的

- **扫网段**:像横向渗透,会触发企业 EDR。这是安全立场,不是性能取舍(ADR-0005)。"广播"不是它的同义词,别混用。
- **跨网发现 / 服务器中转**:与无服务器架构冲突。
- **IPv6**:当前多播地址是 IPv4 的,只支持 IPv4。
- **多播报文伪造 / 放大攻击的防护**:发现层 DoS 不处理。
- **防主动冒充**:身份广播本身是明文,同网段的主动攻击者可以冒充任意名字与指纹,发送方无从察觉(与官方 LocalSend 同级局限)。**接收前的人工确认是唯一防线**——请在可信局域网使用。
- **对上面 F 组网络环境的兜底**:见那条推论,应用层无解。

## 已知缺口

- **运行期发现丢失,根因未实锤**:能正常发现,几分钟后双向消失,需重启才恢复。怀疑多播组老化或 socket 僵死,**尚未抓包坐实**。这是目前发现层最大的未知。
- **回应报文省略端口这条约束没有自动化用例守**:它写在不变量里,靠人守;违反的后果是连错端口,而症状会表现为"发现得到但发不过去",与 VPN 那条撞脸。
- **网络环境限度靠人工实测**,没有回归保护:哪天改动破坏了双通道中的一条,自动化测试不会红。
- **macOS 本地网络权限**的授权流程没有自动化验收。
